Модуль 1. Базовые конструкции Java и Kotlin (Неделя 2-3)
Цель: Научиться писать чистые, читаемые функции и работать с данными. Мы не учим синтаксис ради синтаксиса — мы учимся сразу писать «тестируемый код».

Теория (Блок 1):

Java: Примитивы и ссылочные типы, immutable-объекты (final), циклы, условия.

Kotlin: В чем его сила? Null-safety (?, !!, ?:), Data-классы (замена POJO), функции-расширения.

Важное отличие: В Kotlin все — выражение (if возвращает значение). Это сокращает код и уменьшает количество багов.

Пример кода (Сравнение):
Java:

java
public String getStatus(boolean isActive) {
    if (isActive) {
        return "Active";
    } else {
        return "Inactive";
    }
}
Kotlin:

kotlin
fun getStatus(isActive: Boolean) = if (isActive) "Active" else "Inactive"

Модуль 2. ООП, Паттерны и Работа с памятью (Неделя 4-5)
Цель: Понять, как проектировать систему так, чтобы ее легко было тестировать (Dependency Injection).

Теория:

SOLID: Особенно буква D (Dependency Inversion). Мы не создаем объекты через new внутри классов — мы их инжектируем (передаем в конструктор). Это основа для Mockito.

Паттерн Repository: Прослойка между данными (API/БД) и UI.

Исключения: Проверяемые (Java) и непроверяемые (Kotlin). Обработка ошибок — это часть тест-плана.

Разбор реальной практики:
Представь, что ты тестируешь экран логина. Если внутри экрана жестко зашит сетевой вызов (new Retrofit()), ты не сможешь написать Unit-тест (он будет стучаться в реальный сервер). Мы делаем так:

kotlin
// Плохо (жесткая связь)
class LoginViewModel {
    private val api = RetrofitBuilder.build() // НЕ ТЕСТИРУЕМО!
}

// Хорошо (слабая связь)
class LoginViewModel(private val repository: AuthRepository) {
    // В тестах сюда придет FakeRepository, а не реальный
}
Практика:

Создай интерфейс UserRepository.

Реализуй два класса: RealUserRepository (работает с фейковым API через Thread.sleep()) и FakeUserRepository (возвращает заранее заготовленные данные).

Напиши класс UserPresenter, который в конструктор принимает этот репозиторий и метод loadUser(), который вызывает репозиторий.

Задание: Убедись, что при замене RealUserRepository на FakeUserRepository логика презентера не меняется.

Доп. библиотека: Внедри Dagger 2 или Koin (выбери Koin — проще для старта) для автоматической сборки зависимостей.

Модуль 3. Android: От Activity до Retrofit (Неделя 6-8)
Цель: Научиться создавать UI и интегрировать сторонние ресурсы (библиотеки).

Теория:

Жизненный цикл Activity/Fragment: onCreate, onStart, onResume, onPause, onDestroy. Где инициализировать ViewModel, а где подписываться на данные.

Jetpack Compose: (Современный подход) — мы пишем UI декларативно. Это проще для тестирования.

Работа с сетью: Библиотека Retrofit + OkHttp. Интерсепторы для логирования.

Асинхронность: Coroutines (Kotlin) — легковесные потоки. suspend функции, launch, withContext.

Пример кода с интеграцией:

kotlin
// Запрос к API с использованием Coroutines
interface ApiService {
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: Int): User
}

class UserRepository(private val api: ApiService) {
    suspend fun fetchUser(id: Int): Result<User> {
        return try {
            Result.success(api.getUser(id))
        } catch (e: Exception) {
            Result.failure(e)
        }
    }
}

Модуль 4. Unit-тесты и TDD (Неделя 9-10)
Цель: Научиться покрывать логику (не UI) тестами. Это будет твоей новой привычкой.

Теория:

JUnit 5: Аннотации @Test, @BeforeEach, @DisplayName.

Mockito / MockK: Создание моков (заглушек) для зависимостей.

Правило: Не тестируем конструкторы, геттеры и сеттеры. Тестируем поведение.

TDD (Test-Driven Development): Сначала пишешь тест (который падает), потом пишешь минимальный код, чтобы тест прошел.

Разбор кода (Тестируем логин):

kotlin
// Класс, который мы тестируем
class LoginUseCase(private val repo: AuthRepository) {
    suspend operator fun invoke(login: String, pass: String): Boolean {
        return repo.authenticate(login, pass).isSuccess
    }
}

// Тест (используем MockK)
@Test
fun `given valid credentials when login then return true`() = runTest {
    // Given (подготовка)
    val mockRepo = mockk<AuthRepository>()
    coEvery { mockRepo.authenticate("user", "123") } returns Result.success(Unit)
    val useCase = LoginUseCase(mockRepo)
    
    // When (действие)
    val result = useCase("user", "123")
    
    // Then (проверка)
    assertTrue(result)
    coVerify(exactly = 1) { mockRepo.authenticate("user", "123") }
}
Практика:

Возьми класс Calculator, который ты писал в модуле 1.

Напиши для него тесты: проверка деления на ноль, проверка суммы больших чисел.

Модуль 5. UI-тесты и E2E (Неделя 11-12)
Цель: Автоматизировать взаимодействие пользователя с экраном.

Теория:

UI-тесты (Инструментационные): Espresso (для одного приложения). Ищет элементы по id или тексту, выполняет клики, проверяет отображение.

UI Automator: Для тестирования взаимодействия между несколькими приложениями (например, открыть камеру или галерею).

E2E (End-to-End): Это связка UI-тестов с реальным бекендом (или тестовым стендом). Мы прогоняем сценарий: Запуск -> Логин -> Покупка -> Выход.

Пример Espresso-теста:

kotlin
@Test
fun loginButton_clicked_showWelcomeScreen() {
    // 1. Найти поле ввода логина и ввести текст
    onView(withId(R.id.etLogin)).perform(typeText("testuser"), closeSoftKeyboard())
    // 2. Найти кнопку и нажать
    onView(withId(R.id.btnLogin)).perform(click())
    // 3. Проверить, что появился новый экран
    onView(withId(R.id.tvWelcome)).check(matches(isDisplayed()))
}
Важно: Используй IdlingResource для ожидания ответа от сервера, иначе тесты будут "флакать" (падать случайно).

Практика:

Напиши Espresso-тест на экран логина: проверь валидацию (пустой пароль -> кнопка неактивна).

Напиши тест на список постов: проверь, что RecyclerView/Compose LazyColumn отображает хотя бы один элемент после загрузки.

E2E-задание: Напиши сквозной тест, который логинится через UI, делает запрос к реальному API (тестовому) и проверяет, что в БД Room появилась запись.

Доп. библиотека: Barista (надстройка над Espresso для упрощения синтаксиса) или Kaspresso (для лучшей стабильности и логирования).

Модуль 6. Интеграция, CI/CD и Финальный проект (Неделя 13-14)
Цель: Собрать всё в единый пайплайн.

Теория:

GitHub Actions / GitLab CI: Автоматический запуск всех тестов (Unit + UI) при пуше в ветку main.

Сборка артефактов: Генерация APK/AAB для релиза.

Code Coverage: Подключаем плагин Jacoco для отслеживания процента покрытия кода тестами (цель — > 80%).

Финальный проект (Твой диплом):
Ты создаешь Todo-приложение (или менеджер паролей) со следующими требованиями:

Архитектура: MVVM + Clean Architecture (слои Data, Domain, Presentation).

Сторонние ресурсы: Retrofit (синхронизация с облаком) + Room (локальное хранилище) + Dagger/Koin.

Unit-тесты: Покрыть все UseCase и ViewModel (используя фейковые репозитории).

UI-тесты: Написать 3 ключевых сценария (Добавить задачу, Удалить задачу, Отметить выполненной).

E2E: Сценарий синхронизации (добавил офлайн -> вышел в интернет -> данные улетели на сервер).

Git: Работать через Pull Requests, каждый фича-флаг в отдельной ветке.
